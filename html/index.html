5/20/26: A recipe-sharing web application designed for users to share recipes and collaborate on writing up recipe documents in real-time. This project was one that ended up in failure, so why put it on my portfolio? It taught me quite a few things in the process.

Software projects can fail. And that's okay. It's something that any developer should experience atleast once in their life.

Here's my perspective on why it failed:
- shaky or unclear user requirements
- lack of clear direction for the team
- lack of motivation to work on the project
- lack of technical ability

We did pretty well in the initial design phases. Hardly any coding was involved, and it seemed like our mockups, user stories, and initial requirements seemed solid.

It was during the UI/UX Figma design phase and coding phase where we started declining and going downhill. The biggest problem here was a lack of communication and discipline to meet deadlines.

What I should've done:
- took action as early as possible and address these problems with team members in one-on-ones . This asks why the motivation problem exists in the first place, and is different for each member.
- provide team members with learning resources and help them by hosting workshops. This would've helped with the technical ability problem.
- being more realistic with our requirements. Nearing the end of the project, we realized we didn't have the time to complete some of our initial requirements because we haven't done enough research and realized implementing some features would've been tough.

5/20/26: An excuse to start working with the Zephyr RTOS environment. After a 1 month break since pausing on the bare-metal mp3 in April, I've decided to rewrite it while integrating Zephyr RTOS. There really is no good reason as to why use an RTOS for this project. This isn't the kind of project where real-time constraints are super critical. It can totally be done with a simple super-loop and interrupt architecture. However, I wanted to learn RTOS, and so here we are.

The multi-threaded architecture that comes with working with an RTOS might allow me to do music visualization, audio playback, and user-input as three concurrent tasks. I'm also using NRF Connect SDK, which provides many abstraction layers such as KConfig, DeviceTree, and peripheral libraries. KConfig is used within the build system to configure software components, and decide which software modules to include from Zephyr's libraries. DeviceTree can be thought of as a collection of files that describes the hardware components of a system to the Zephyr RTOS, so as to keep the hardware configs separate from the application source code. This allows application code to be written in a portable way (given that you stay within the Zephyr ecosystem and support for a given board is provided).

The MCU I plan to work with is the nRF52840, which comes with a 2.4GHz radio transceiver for BLE applications. With that I'll try to implement BLE audio streaming to earbuds that support the Bluetooth Low Energy protocol. Keep in mind that the radio doesn't support Bluetooth Classic, which most headphones support. This is a heavy downside and an oversight on my part when I was selecting a board to work with.

4/4/2026: I've implemented the core functionalities which consist of filesystem navigation and audio playback. I'm at a good checkpoint to take a break from this project. 4 months of consistently tackling a project is enough for anyone to lose motivation. Instead of glazing my project and highlighting what works, I'm going to be my own worst critic and tell you what doesn't work! But first, let me just go over the requirements of the project; how the system was intended to work in mind.

On power up, the system would boot into a state where the root directory of the filesystem on the SD card would be displayed on the small screen. From there, the user could navigate through the directories using button controls, and select a valid mp3 file to start playing audio.

Upon selecting an mp3 file, the system transitions into an audio playback state, where the mp3 audio starts playing through the DAC. A speaker or headphone needs to be connected to the DAC. Again, with the buttons, the user can choose to pause/play the audio, or go back to the filesystem navigation state.

Now to reflect on what has been implemented as of writing. I haven't fully fleshed out the state transitions between the filesystem navigation and media player states. But in isolation, both states work as intended. Filesystem can be navigated, and audio is playing as intended. Hooking up the state machines on the software side of things is pretty trivial, but I just haven't done it because there are bigger fish to fry.

The biggest source of my frustration, and the issue that has been plaguing me for a while is getting the audio to sound "GOOD", while minimizing power consumption.

As of now, the audio coming out of the DAC is pretty grainy and choppy. I've isolated the issue to be a producer-consumer problem, where the DAC is consuming audio data from a double-buffer faster than it can be produced from the SD card. This results in the DAC consuming "old" audio data, which results in grainy audio.

Essentially my SPI reads from the SD card isn't fast enough. However, I have the SPI clock rate clocked at around 11MHz, which seems to be the maximum allowed for my given hardware. That's around 11Mbps throughput. Raising my system clock at such a high frequency results in higher power consumption, which is not ideal in embedded. We always want to use less power than needed. Those 11Mbps data are compressed mp3 file chunks that require on-board decoding, and produces uncompressed pcm audio chunks ready for the DAC to consume. This is the actual producer rate, which may be significantly lower than 11Mbps. While my DAC is consuming data at around (16*2)* (48000kHz) = 1.536Mbps. There are also alot more factors that slow down the "producer rate" such as the CPU having to process other tasks in sequence.

I could probably gain more accurate timing information if I had an oscilloscope, but they cost a pretty penny. I'm definitely doing something wrong here, theres room for improvement. Mp3 players have been around since the early 2000s, and they had hardware that were less powerful than the STM32 microcontroller that I'm using today.

I'm taking a hiatus on this project because frankly, I'm tired of it. But once I feel like it, I'll pick it back up.
